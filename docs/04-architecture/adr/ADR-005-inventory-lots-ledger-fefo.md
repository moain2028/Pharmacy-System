# ADR-005: المخزون — Lots + Immutable Ledger + FEFO + SSU Integer

- **الحالة:** Accepted — 2026-11-03
- **القرار المرتبط:** D-005, D-007, D-020
- **المتطلبات:** CH-F09 (منصور)، CH-N04 (مازن)، FR-INV-001..013
- **البحث:** R6

## السياق
الواقع: نفس الصنف يصل بتواريخ انتهاء وأسعار مختلفة (بما فيها الموازي). البرامج الشائعة تخزن كمية واحدة قابلة للتعديل → لا تتبع، تلاعب، أرباح خاطئة.

## القرار
1. **Lot لكل سطر استلام** (`expiry_date`, `unit_cost`, `supplier_id`, `source_type`).
2. **`stock_movements` append-only** (Trigger يمنع UPDATE/DELETE)؛ `qty_delta INTEGER` بالـ SSU؛ كل حركة بمرجع.
3. **الرصيد مشتق** = SUM؛ `stock_balances` projection يُحدَّث في نفس Transaction وقابل لإعادة البناء.
4. **FEFO** افتراضي عبر `FefoAllocator`؛ تجاوز بصلاحية + سبب.
5. **لا بيع منتهٍ؛ لا سالب** إلا بسياسة.
6. سطر الفاتورة يحفظ `lot_id` و`unit_cost` → ربح دقيق لكل سطر.
7. تواريخ الدفعة: `expiry_date`, `alert_date` (مشتق؛ افتراضي 90 يوم)؛ `removal_date` اختياري مستقبلاً.

## البدائل المرفوضة
- كمية قابلة للتحديث في `items`: يفقد التاريخ ويسمح بالتلاعب.
- FIFO: يتجاهل الانتهاء — غير مناسب للأدوية.
- دمج الدفعات بنفس الرقم: يخفي اختلاف التكلفة.

## النتائج
- ✅ تتبع كامل، جرد موثوق، تقرير حركة مجاني، ربح دقيق.
- ✅ يسهّل المزامنة (الجمع تبادلي).
- ⚠️ حجم بيانات أكبر (مقبول: مليون حركة = ~200MB).
- ⚠️ تعقيد الواجهة يُخفى (FEFO تلقائي؛ الدفعة معلومة ثانوية).
